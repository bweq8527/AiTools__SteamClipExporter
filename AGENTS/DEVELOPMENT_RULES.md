# 开发与维护规范

用户约束的权威来源为 [REQUIREMENTS.md](REQUIREMENTS.md)；每次会话启动／完成／交接按根 `AGENTS.md` 执行。下列规则不授权新功能或业务修复。

## 需求和修改范围

1. 先核对工作区、近期提交、相关需求和实际调用链，简要说明理解。文档与代码冲突要明确指出；用户意图优先，代码仅证明现状。
2. 新功能明确验收、冲突和影响后先提出方案，等待用户确认。复杂任务建档；用户已确认的具体范围无需重复申请同一授权。
3. 只改当前任务需要的文件；禁止无关重构、批量格式化、安装、升级或新框架。保持现有 API、路径规则、导出命名、选择顺序等兼容；若需改变，先说明并确认。
4. 保留用户已有修改和未跟踪文件；不要自行清理缓存、改 Git 忽略、改目录布局或覆盖已有资料。写入／删除真实媒体须有相应授权。
5. 已完成的记忆初始化任务仅修改根入口和 `AGENTS/` 内 Markdown；后续任务按当次用户授权限定范围。本次导出目录与同步修复已获准，其他已知问题不顺手修复。

## 风格与模块边界

- 当前代码主要为 Python 函数式模块和原生 JS，沿用邻近文件风格。Python 已有 `snake_case` 函数和大写全局状态，JS 主要 `camelCase`；遗留 `set_p/list_c/add_q` 等名称保留，不能为统一命名无关重命名。
- 未发现既有 linter／formatter 配置，不宣称项目已采用 Black、Ruff、ESLint 等。新规范或工具需有实际必要性与授权。
- `app.py` 负责 HTTP／桌面交互和队列，`worker.py` 负责媒体处理，`frontend/` 负责交互展示。改动先定位职责，不未经讨论强制拆层或引入框架。
- 备注写清原因、约束与边界；不复制源代码或堆积无效解释到记忆文档。

## 错误处理、安全和数据

- 不能把“请求成功”“子进程退出”“文件存在”混同为业务成功。修改错误路径时明确 API 状态、日志、临时文件和输出残留处理。
- 校验 JSON 类型、目录、cid 与路径边界；调用 FFmpeg 保持参数数组，避免拼接 shell 命令。系统打开、覆盖输出和清理文件须限制在获准范围。
- 保持本地使用前提，不擅自改为公网监听或开放远程访问；当前 CORS／无鉴权现状不代表安全评估通过。
- 不在文档、测试资料或日志样例中保存密码、Token、API Key、个人路径／账号资料或真实敏感媒体。迁移使用相对路径，示例应脱敏。
- FFmpeg／FFprobe 与打包工具版本、分发许可和支持环境需按真实证据说明，未经核实不保证兼容或许可状态。

## 测试与证据

- 按变更风险做必要验证，不为简单文档／低影响改动引入测试框架或安装依赖。不得用“应当正常”冒充实测。
- 文档任务：检查结构、链接、函数／路由依据、跨文档一致性与交接问题；对照 Git diff 和原文件校验，确认业务未改。
- 后续 Python／JS 改动：先做语法检查，再按修改验证受影响 API、正常和错误路径。媒体操作使用隔离样例及独立导出目录；验收输出播放、时长／音轨、状态、进度及临时文件处理。测试样例与断言应检验真实行为，不机械镜像实现。
- 启动／打包改动：分别验证桌面、浏览器与目标 EXE 的适用路径；不能把语法通过写成运行／构建通过。安装和构建只能在获准范围执行。
- 记录命令、结果和未验证范围；应用 import 会启动 worker，bat 会尝试安装，`build.py` 会写入及清理，选择验证方式前考虑副作用。

## GitKraken 与文档维护

AI 默认只读 Git 状态／历史／diff，不执行暂存、commit、push、reset、rebase、切分支、stash、清理或全局配置修改；用户通过 GitKraken 手动管理。遇到所有权限制可用只对单次只读命令生效的 `git -c safe.directory=<已核实项目路径> ...`，不持久改安全配置。

任务完成后检查真实 diff，更新当前状态、交接和实际受影响的知识；重要变更写 CHANGELOG，需求／架构／决策变化分别写其主要文件，已完成任务移到 COMPLETED。只读提问无需更新。入口和动态快照保持简短，历史留任务档案。用户手动提交后，下次接手读取当前 Git 事实即可，不为追写文档自身提交哈希制造循环修改。

交接触发语和失败处理按根规则 D；无法保存文件时明确给出可复制的交接内容并说明尚未落盘，不能伪称已保存。
